# AI pipeline contracts and benchmark practices

Research date: 2026-09-27. Read-only inspection of SwiftSci at `ab7aa2f1dab7256eed5de177fb5060a25740c643`; no tests or benchmarks were run. External evidence below comes from project documentation and actual test or benchmark code. Versioned links identify the consulted release where available; `main` and `stable` links are moving references, not dependency pins.

SwiftSci should strengthen the complete native Apple silicon pipeline before expanding its model catalogue. The useful lessons from scikit-learn, PyTorch, JAX and MLX are specific contracts: preprocessing fitted only on training rows, prediction consistency after loading, tensor metadata checked alongside values, and timing that includes completed work. They do not require reproducing those frameworks.

## Transfer the estimator contracts

Scikit-learn directs users to split before preprocessing and fit transformations only on training data. Its guidance also distinguishes a reproducible splitter seed from estimator randomness across folds. SwiftSci already follows the first rule in frozen fixtures. Extend that protection to the public pipeline: perturb validation/test values, rerun preprocessing and fitting, and require unchanged learned state. Keep feature selection, imputation and resampling inside each training fold when those steps enter a workload. [Common pitfalls](https://scikit-learn.org/1.8/common_pitfalls.html).

Repeated timing samples and repeated cross-validation answer different questions. For a predictive-quality workload, freeze repeated fold assignments and estimator seeds, then compare both implementations on identical folds. Use group or temporal boundaries when the scientific sampling process requires them; stratification alone does not prevent related observations crossing partitions. Select parameters on training/validation evidence and reserve a fresh final evaluation set. Scikit-learn's [RepeatedStratifiedKFold](https://scikit-learn.org/1.8/modules/generated/sklearn.model_selection.RepeatedStratifiedKFold.html) explicitly varies randomization across repetitions. SwiftSci's existing balanced-fold test should be extended with disjointness, complete membership and repeat-seed checks, rather than replaced.

Scikit-learn's actual estimator checks exercise probability shape, row sums, consistency with predicted classes, feature-count errors and prediction preservation after pickling. Adopt a small equivalent contract for the estimators SwiftSci actually uses. Specify class-column order, positive label, finite probability bounds and tie handling explicitly; binary 0.5 behavior must remain the declared strict threshold. Then serialize the fitted scaler and estimator together, reload in a fresh process and compare every prediction and probability. Existing export-file checks are a useful starting point. [Estimator checks, release 1.8.0](https://github.com/scikit-learn/scikit-learn/blob/1.8.0/sklearn/utils/estimator_checks.py).

One concrete API concern is the fixed-weight `LinearRegression` initializer: it stores CPU weights and bias without setting `resolvedDevice`, while prediction selects those weights only when that device is CPU. Review this initializer-to-prediction contract and preserve its reported failure; it does not establish that all training is broken. [Initializer and prediction implementation](/Users/crabel/Documents/src/SwiftSci/Sources/SwiftML/Core/LinearRegression.swift).

Record model-format version, training-data digest, feature schema, class mapping, preprocessing state and dependency versions. Scikit-learn explicitly does not support loading persisted estimators across arbitrary library versions. SwiftSci needs its own supported compatibility contract, including rejection of missing weights and wrong dimensions. [Model persistence](https://scikit-learn.org/stable/model_persistence.html).

## Transfer the tensor and randomness contracts

PyTorch separates operator integration checks from derivative checks. `opcheck` verifies declared mutation, tensor metadata and eager/compiled behavior; `gradcheck` tests the mathematical gradient. Its documentation recommends representative inputs on every supported device. For SwiftSci, use the same separation without importing PyTorch's registration machinery: independently check values, shapes, dtypes, requested devices, aliasing and supported broadcasting. Add finite-difference or analytic derivatives only where SwiftSci exposes trainable operations. A forward-logit pass cannot establish backward correctness. [PyTorch operator testing](https://docs.pytorch.org/docs/2.14/library.html#testing-custom-ops).

Apple's own tests give concrete examples. MLX checks NumPy agreement for broadcasting, rejects negative broadcast dimensions, and tests reductions of singleton-leading shapes. MLX Swift checks first and second derivatives of a square and a seeded nested-module loss with gradient dictionary structure. These are good patterns for a compact SwiftSci operation matrix around affine conversion, normalization, attention and cache updates. [MLX operation tests](https://github.com/ml-explore/mlx/blob/main/python/tests/test_ops.py), [MLX Swift transformation tests](https://github.com/ml-explore/mlx-swift/blob/main/Tests/MLXTests/TransformTests.swift).

Pin randomness separately from arithmetic tolerance. JAX makes random keys explicit and warns that reusing a key repeats or correlates samples. PyTorch does not promise identical results across releases, platforms or CPU/GPU even with the same seed. SwiftSci should record initialization, split and sampling seeds independently, test replay within the declared environment, and check cross-device numerical agreement with justified tolerances. Fixed stored weights should remain the neural conformance default. [JAX random keys](https://docs.jax.dev/en/latest/random-numbers.html), [PyTorch reproducibility](https://docs.pytorch.org/docs/2.14/notes/randomness.html).

## Measure completed work and useful inference

MLX records lazy graphs until evaluation; unused outputs may never execute. JAX requires `block_until_ready()` for asynchronous execution, separates first-call compilation and transfer costs, and warns that its default 32-bit types can make an uncontrolled NumPy comparison unfair. SwiftSci's current evaluation, synchronization and complete extraction are strengths to preserve. Add separate cold-start and warmed execution contracts with exactly stated loading, allocation, compilation and readback boundaries. [MLX lazy evaluation](https://ml-explore.github.io/mlx/build/html/usage/lazy_evaluation.html), [JAX benchmarking](https://docs.jax.dev/en/latest/benchmarking.html).

PyTorch's timer performs warmups, controls thread-pool size and synchronizes asynchronous accelerators. Record thread counts, backend, dtype, machine, power conditions and dependency versions in SwiftSci comparisons. Report distributions across independent runs rather than treating two checked samples as a stable speed estimate. CPU NumPy remains a numerical reference for GPU-requested Swift results, not a matched-backend speed comparison. [PyTorch benchmark utilities](https://docs.pytorch.org/docs/2.14/benchmark_utils.html).

MLX-LM's actual benchmark varies prompt length, generation length and batch size, performs a warmup and repeated trials, and reports prompt throughput, generation throughput and peak memory. It generates random prompts, so that performance exercise alone establishes no language quality. SwiftSci should add a sustained workload only after cache correctness: several context lengths, multi-token continuation after populated caches, batch sizes, cache reset and growth, time to first token, per-token latency distributions, total latency and throughput. Pair each configuration with held-out quality evidence when a real model is introduced. [MLX-LM benchmark code](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/benchmark.py).

Keep process peak RSS distinct from MLX allocator memory and logical tensor bytes. MLX's peak is measured since program start or the last reset; report the reset boundary and whether model loading and cache allocation fall inside it. Add sustained runs long enough to observe memory growth and thermal effects. Neither a 4 MiB conversion sweep nor subtracting two RSS peaks measures copy overhead. [MLX peak memory](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.get_peak_memory.html).

MLPerf supplies a useful discipline: declared datasets, quality targets, scenarios, load generation and latency constraints. Its rules include TTFT and time-per-output-token requirements for specified generative workloads. Borrow that measurement discipline, but call a SwiftSci custom workload exactly that. Official MLPerf results require the applicable approved rules, LoadGen, accuracy/compliance evidence and submission process. Numerical conformance, predictive quality and official benchmark standing are separate claims. [MLPerf overview](https://mlcommons.org/benchmarks/inference-datacenter/), [inference rules](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc).

## Proposed order

1. Complete the test contracts and diagnostics for retained loader and cached-RoPE failures. Preserve independent full-output checks and explicit device requirements. Repair production code later on the separate repair branch.
2. Complete one tabular workflow with public-pipeline leakage tests, repeated paired splits, probability semantics and fresh-process serialization parity.
3. Extend dataframe-to-tensor measurements to representative production sizes; quantify completed conversion and inference separately, then measure the whole pipeline.
4. Add one sustained decoder workload and one spatially varying vision-resize contract. Resolve input-range and interpolation semantics before comparing vision implementations.
5. Introduce one licensed pretrained checkpoint only when loader, tokenizer, quality set and tolerances are frozen. Then establish the formal baseline with quality and latency measured together.

Defer broad training suites, distributed execution and model-zoo expansion until a concrete native scientific workload needs them. A small collection of independently checked end-to-end workloads will answer more useful questions than a large catalogue of unqualified timings.
