# Dataframe evidence for SwiftSci's scientific workflow

SwiftSci should qualify a specific path: scientific files become typed columns, selected rows remain aligned with targets, and matrices become valid CPU or GPU model inputs. pandas, Polars and Arrow offer useful testing practices for that path. Their full feature sets are unnecessary acceptance targets. This review read upstream documentation and source, plus SwiftSci's benchmark contracts, fixtures, controller tests and selected library tests. It ran no benchmarks. Upstream source links below pin pandas at `57a9b2026c5673f2071417f2b37bba5d1bb1149d`, Polars at `72f7d3b8aebfc5b2899d4418e8dbbf96d872a693`, and Arrow at `a99c14ed5ee9dd183b60e66c0daa5301d75dcb4b`, retrieved on 2026-09-27. Documentation can describe different releases.

The supplied acceptance snapshot has 22 profiles, 1,132 executions, 1,102 passes, 30 failures and 135 controller tests. Those totals describe the recorded scope, not universal dataframe correctness. SwiftSci already separates correctness from performance eligibility, retains failed evidence, checks experiment compatibility and describes its certificate as unsigned local conformance. Its bounded table-to-model sweeps separate conversion, prepared arithmetic and full pipeline measurements. At a maximum logical matrix size of 4 MiB, these demonstrate measurement mechanics rather than large-data performance. [SwiftSci benchmark contracts and reporting](</Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/README.md>), [sweep workload](</Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/Specs/workloads/dataframe-model-sweep-v1.json>).

The 24-case dataframe semantic profile is substantive. Independent scalar answers check Int64 beyond 2^53, missing versus present NaN, signed zero, null-last stable sorting, composite group keys, first-appearance order, built-in column replacement isolation and non-square row-major matrix export. Integer word encoding prevents the comparison transport from hiding precision loss. The pandas adapter deliberately normalizes behavior to SwiftSci's contract, so its tiny fixture timings are not pandas-default performance results. Keep these guarantees. Add explicit semantic cases where intended scientific workflows require them. [Fixture contract](</Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/Fixtures/dataframe/README.md>), [controller assertions](</Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/Tests/test_dataframe_fixtures.py>).

pandas makes a useful distinction between inexpensive parametrized examples and Hypothesis generation for complicated interactions. Its actual merge tests cross missing keys, dtype preservation, categoricals, timezone transitions and output order. pandas also explicitly matches null join keys to each other. A pandas result is therefore an oracle only after choosing matching semantics; merely running the same operation name proves little. [Testing guidance](https://pandas.pydata.org/pandas-docs/stable/development/contributing_codebase.html), [pinned merge tests](https://github.com/pandas-dev/pandas/blob/57a9b2026c5673f2071417f2b37bba5d1bb1149d/pandas/tests/reshape/merge/test_merge.py), [merge contract](https://pandas.pydata.org/docs/reference/api/pandas.merge.html).

For SwiftSci, the next semantic acceptance set should cover duplicate-key join multiplicity, missing-key policy, empty joins, output column collisions and target alignment after joins. Preserve exact integers and null masks before conversion. Add Unicode keys, empty strings and canonically equivalent strings with a declared equality policy. Categories need stable training/inference encodings only if that workflow uses categorical features; a label column named "category" does not test dictionary metadata. Timestamp units, timezone conversion and daylight-saving ambiguity belong in acceptance when timestamps become model features. Explicit unsupported behavior is acceptable. Existing typed join tests, Unicode uniqueness checks, Date sorting, Arrow conversions and PyArrow-generated Parquet fixtures mean these are standardized-suite coverage gaps, not evidence that SwiftSci has no tests for these areas. [Join tests](</Users/LOCAL_USER/Documents/src/SwiftSci/Tests/SwiftDataFrameTests/SIMDJoinTests.swift>), [type and Unicode tests](</Users/LOCAL_USER/Documents/src/SwiftSci/Tests/SwiftDataFrameTests/DataFrameAPIExtensionTests.swift>), [external Parquet tests](</Users/LOCAL_USER/Documents/src/SwiftSci/Tests/SwiftDataFrameTests/ParquetInteropTests.swift>).

Polars combines generated data with concrete assertions. Its NumPy conversion test generates temporal series, exports with copying forbidden, compares the NumPy address to the Arrow values buffer, and asserts that the result is read-only. Nearby tests check C/F layout and copying requirements. This is stronger evidence for a zero-copy claim than equal values. Its documented testing tools supply dtype-aware dataframe and series strategies. [Pinned NumPy tests](https://github.com/pola-rs/polars/blob/72f7d3b8aebfc5b2899d4418e8dbbf96d872a693/py-polars/tests/unit/interop/numpy/test_to_numpy_df.py#L22-L68), [testing API](https://docs.pola.rs/api/python/stable/reference/testing.html), [conversion contract](https://docs.pola.rs/api/python/stable/reference/dataframe/api/polars.DataFrame.to_numpy.html).

Borrow the method before pursuing zero-copy optimization. Proposed acceptance is a reproducible generated suite over supported types, null masks, extreme integers, nonfinite floats, row permutations and chunk boundaries. Check filter/gather equivalence, feature/target identity, nested/flat export equivalence and source isolation against an independent scalar model. Record seeds, minimize failures and retain them as fixed fixtures. Generation must run in a named CI tier. SwiftSci already has deterministic random-byte CSV serial/parallel parity tests, plus compensated grouping tests for cancellation, infinities and subnormals. Expand that foundation; do not call property-based coverage absent. [Randomized parser test](</Users/LOCAL_USER/Documents/src/SwiftSci/Tests/SwiftDataFrameTests/CSVParallelScanTests.swift:60>), [grouping accuracy tests](</Users/LOCAL_USER/Documents/src/SwiftSci/Tests/SwiftDataFrameTests/CompensatedGroupingTests.swift>).

Arrow supplies both an interoperability specification and concrete integration machinery. Its cross-language tests exchange generated or gold fixtures through supported producer/consumer pairs. C Data Interface tests can check memory after release. Its C interface requires producer-managed storage, release callbacks and immutable exported buffers. This makes lifetime a separate contract from values. [Integration testing](https://arrow.apache.org/docs/format/Integration.html), [C Data Interface](https://arrow.apache.org/docs/format/CDataInterface.html).

The pinned Arrow bridge test records allocator bytes, exports an array, destroys the original owner, verifies that exported storage remains alive, then releases the export and checks that memory returns to its original level. Other assertions detect repeated release, sliced offsets and malformed structures. SwiftSci should adopt equivalent tests for whichever bridge it actually exposes, without presuming its Swift ArrowTable bridge implements the C interface. Proposed acceptance covers supported types in both external directions, sliced/null bitmap offsets, producer destruction, consumer destruction, repeated conversion and promised mutation isolation. Report copying explicitly. Defer a zero-copy label until buffer identity, lifetime and supported layouts are demonstrated. [Pinned ownership tests](https://github.com/apache/arrow/blob/a99c14ed5ee9dd183b60e66c0daa5301d75dcb4b/cpp/src/arrow/c/bridge_test.cc#L680-L712), [SwiftSci Arrow tests](</Users/LOCAL_USER/Documents/src/SwiftSci/Tests/SwiftDataFrameTests/DataFrameArrowTests.swift>).

Parser robustness should test more than agreement between two paths that share code. Arrow's CSV fuzz target exercises serial, threaded and streaming readers with small blocks, then validates the entire resulting table. It also waits for background tasks before borrowed input memory disappears. Arrow recommends retaining known fuzz failures and testing invalid offsets and UTF-8. [Pinned CSV fuzzer](https://github.com/apache/arrow/blob/a99c14ed5ee9dd183b60e66c0daa5301d75dcb4b/cpp/src/arrow/csv/fuzz.cc#L38-L86), [robustness guidance](https://arrow.apache.org/docs/dev/format/Security.html). For SwiftSci, first fuzz its supported CSV and Parquet ingestion under available sanitizers, with valid seed files, malformed/truncated data, oversized fields and quoted chunk boundaries. Acceptance should record a bounded campaign, no crashes or sanitizer failures, explicit rejection behavior, and regression fixtures for every discovered defect. A completed campaign is bounded evidence, not proof against all malformed files.

Performance work should preserve SwiftSci's correctness gate and add realistic shapes. pandas uses ASV history and warns that machine load changes results; its benchmark sources vary dtype, ordering and missingness, and include explicit peak-memory methods. Arrow supports saved baseline comparisons and repeated measurements, distinguishing wall time from CPU time for parallel work. [pandas benchmark policy](https://pandas.pydata.org/community/benchmarks.html), [pinned join benchmarks](https://github.com/pandas-dev/pandas/blob/57a9b2026c5673f2071417f2b37bba5d1bb1149d/asv_bench/benchmarks/join_merge.py), [pinned memory benchmarks](https://github.com/pandas-dev/pandas/blob/57a9b2026c5673f2071417f2b37bba5d1bb1149d/asv_bench/benchmarks/frame_methods.py#L180-L232), [Arrow benchmark controls](https://arrow.apache.org/docs/developers/benchmarks.html).

Polars' streaming tests compare streaming and ordinary execution; its H2O-derived benchmarks exercise grouping combinations. SwiftSci's current CSV streaming workload intentionally groups each chunk independently, so it does not establish global aggregation equivalence. [Pinned streaming comparison](https://github.com/pola-rs/polars/blob/72f7d3b8aebfc5b2899d4418e8dbbf96d872a693/py-polars/tests/unit/streaming/test_streaming_group_by.py#L149-L160), [pinned grouping benchmarks](https://github.com/pola-rs/polars/blob/72f7d3b8aebfc5b2899d4418e8dbbf96d872a693/py-polars/tests/benchmark/test_group_by.py), [SwiftSci streaming contract](</Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/Specs/workloads/csv-stream-group-v1.json>).

The next performance acceptance should use one representative scientific ingestion-to-prediction pipeline plus narrow/wide matrices, skewed groups, duplicate-heavy joins and missing-data variants. Choose sizes from expected workloads and the target Mac's memory budget, including beyond cache. Validate row IDs and predictions throughout. Retain component and full-pipeline times, synchronized GPU completion, cold/warm policy, thread counts, versions, compiler/build identity and raw repetitions. Separate whole-process RSS, allocator activity, logical bytes and device memory. Establish noise with repeated unchanged builds before setting regression thresholds. Keep Kiraa as the documented unofficial research comparator, never a correctness oracle. Defer distributed execution, broad SQL coverage and a full TPC suite until a real SwiftSci use case requires them.
