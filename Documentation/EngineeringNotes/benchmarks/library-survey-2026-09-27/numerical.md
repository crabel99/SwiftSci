# Numerical validation for SwiftSci scientific workflows

Research date: 2026-09-27. Read-only inspection of SwiftSci commit `ab7aa2f1dab7256eed5de177fb5060a25740c643`. Upstream source examples below use explicit release tags for reproducibility, not claims about the latest release. Recommendations are planning proposals; no library, benchmark, or CI changes were made.

SwiftSci should strengthen evidence for a few complete workflows: dataframe preparation, vector and matrix conversion, estimation or solving, and simulation output. The proposed intended-use charter is local scientific analysis on Apple silicon, with explicit Float32/Float64 behavior and reviewable numerical results. Declare readiness for each complete workflow and supported environment. Reproducing the whole SciPy API or an HPC benchmark collection would dilute that work.

## Practices worth adopting

NumPy tests semantics as well as arithmetic. Its guidelines recommend explicit absolute/relative tolerances, strict dtype/shape checks, deterministic random inputs, and Hypothesis for diverse inputs and reduced failing examples. A concrete test in NumPy v2.3.3 passes noncontiguous input and output slices through floating-point classification, covering Float32/Float64, NaNs, infinities, signed zeros, and tiny values. This is a good model for boundary coverage where SwiftSci actually exposes equivalent storage behavior. [Guidelines](https://numpy.org/doc/stable/reference/testing.html); [pinned test](https://github.com/numpy/numpy/blob/v2.3.3/numpy/_core/tests/test_umath.py#L1936-L1985).

An accuracy contract should distinguish exact semantic checks, absolute error near zero, relative error away from zero, and justified ULP bounds for selected elementary calculations. NumPy provides an ULP assertion, but its NaN comparison does not distinguish NaN representations. ULP proximity alone therefore cannot express every IEEE behavior, and a universal ULP cap would be inappropriate for ill-conditioned regression. [ULP documentation](https://numpy.org/doc/stable/reference/generated/numpy.testing.assert_array_max_ulp.html).

SciPy uses independent high-precision references for difficult function regions. Its v1.16.2 complex-erf test uses 70 decimal digits and both linear and logarithmic grids, while beta testing uses 400 digits. Its least-squares tests vary real dtype, LAPACK driver, overwrite setting, and right-hand-side form. The lesson is to select precision and test families deliberately, then retain the reference procedure. A second binary64 library is useful differential evidence, but agreement alone is not an independent accuracy proof. [Special-function tests](https://github.com/scipy/scipy/blob/v1.16.2/scipy/special/tests/test_mpmath.py#L246-L261); [least-squares tests](https://github.com/scipy/scipy/blob/v1.16.2/scipy/linalg/tests/test_basic.py#L1267-L1300).

LAPACK separates the computed answer's error from the problem's sensitivity to perturbation. Its v3.12.1 `DGET02` tests a solution using the 1-norm residual divided by matrix norm, solution norm, and machine epsilon. Other error bounds depend on conditioning and the problem being solved. For SwiftSci, add scaled residual and conditioning evidence beside coefficient comparisons; a small residual need not mean accurate coefficients. Least squares also needs optimality and rank checks, because a nonzero residual can be the correct answer. [Pinned residual routine](https://github.com/Reference-LAPACK/lapack/blob/v3.12.1/TESTING/LIN/dget02.f); [LAPACK accuracy guide](https://www.netlib.org/lapack/lug/node72.html).

SciPy also tests mathematical relationships. Its distribution tests check CDF/inverse-CDF round trips and survival-function identities, then separately assess sampled moments. Such checks can catch inconsistencies without requiring a reference value for every input. They cannot replace independent references because two functions may share a defect. [Pinned distribution tests](https://github.com/scipy/scipy/blob/v1.16.2/scipy/stats/tests/test_continuous_basic.py#L588-L633).

## NIST and conformance limits

SwiftSci already runs all eight NIST linear-regression datasets and eleven balanced ANOVA datasets under two contracts: original-decimal answers and 80-digit calculations on exact binary64 inputs. The latter isolates arithmetic after conversion. Derived predictions and ANOVA p-values are independent calculations, not NIST-certified quantities. Keep both contracts visible. [Fixture contract](/Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/Fixtures/nist-models/README.md).

The recorded failures deserve individual diagnosis. Wampler4/5 fail in both input interpretations for both SwiftSci and the SciPy comparator. SmLs07/08/09 also expose decimal-to-binary64 differences, and SwiftSci has further binary64 ANOVA failures. These are not all conversion failures, and a comparator failing the same threshold does not exonerate either implementation. The fixture contract also records an unobservable analytical-solver fallback to gradient descent. Solver choice, rank policy, stopping behavior, output index, error magnitude, and conditioning would make these failures easier to interpret. [Recorded failures](/Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/Runs/finish-acceptance-02/acceptance.json).

NIST explicitly says passing every StRD dataset does not establish correctness for a user's dataset. Its certified values are best-available solutions for particular computations. Array API compliance addresses a different question: signatures, dtype, shape, promotion, and specified value behavior. Its tests use Hypothesis, allow roughly correct floating-point results, and acknowledge untestable aspects. The suite recommends pinning releases. SwiftSci can borrow its cases, but a Swift API does not acquire Python Array API compliance merely by producing similar arrays. [NIST scope](https://www.nist.gov/itl/sed/statistical-reference-datasets/strd-background-information); [Array API test scope](https://data-apis.org/array-api-tests/).

A local passing record means the declared workload contract passed on the recorded implementation and environment. It does not establish general numerical stability, suitability of a scientific model, validity of observed data, or accreditation.

## Bounded additions and completion criteria

| Priority and user workflow | Proposed evidence | Completion criterion |
| --- | --- | --- |
| 1. Fit a model from prepared columns | Resolve current NIST failures; add well-conditioned, nearly collinear, rank-deficient, scaled, and offset fixtures. Record input interpretation, rank, solver route where observable, residual, and coefficient/prediction errors. | Every existing failure has a reproduced diagnosis and explicit disposition. Required cases pass their predeclared contracts; unsupported rank or solver behavior is reported, not silently accepted. |
| 2. Convert and compute | Extend existing boundary tests with Float32/Float64, missing/nonfinite policy, feature/row permutations, transposed or strided storage where supported, and bounded sparse/dense equivalents. Add representable translation/scale identities for summaries. | Every supported boundary mode has deterministic edge cases plus replayable generated failures. Identity bounds account for rounding and conversion; unsupported layouts are documented. |
| 3. Run a simulation | Select one real scientific simulation or resampling use case. Check generator identity/state, reproducible replay, finite output, relevant analytic moments or known limiting behavior, and uncertainty in Monte Carlo estimates. | Replaying the pinned environment reproduces inputs and declared results. Statistical acceptance uses a predeclared sampling-error budget and failure policy, not repeated runs until one passes. |
| 4. Detect performance regressions | Retain historical results for the same representative pipelines, including small/large dense and one sparse case. Separate conversion, compute, allocation evidence, and total elapsed time. | Repeated baseline runs estimate noise; a controlled regression is detected under a predeclared rule. Correctness failures cannot produce speedup claims. |

Contract analysis and production repair are separate deliverables. First establish input interpretation, conditioning, reference reliability, and the warranted error bound. Then repair any implementation that violates that contract and retain its regression case. Never turn a failing result into a passing one by selecting a tolerance after observing it. A workflow is ready only when its required cases pass; a known unresolved numerical failure blocks that workflow, without making unrelated passing workflows unready. These proposals extend existing contracts rather than replacing them. Finite fixture validators also mean NaN/error semantics may belong in a separate standardized rejection profile instead of forcing nonfinite data into a successful numeric-output contract.

## Reproducibility and performance publication

SciPy uses asv to track runtime, memory, and custom measurements over commit history, with saved comparisons and commit-range investigation. Adopt that historical discipline without requiring a Python-specific controller replacement. [SciPy benchmarking](https://docs.scipy.org/doc/scipy/dev/contributor/benchmarking.html).

Publish the tested minimum and current supported dependency/toolchain combinations. SciPy's toolchain policy illustrates why compatibility spans versions and platforms rather than one developer installation. On Apple silicon, identify actual CPU/GPU execution, Accelerate or other math backend, thread counts, macOS build, chip, compiler, precision, and synchronization boundary. SwiftSci already records much of the host identity; audit backend identity before adding fields. [Toolchain policy](https://docs.scipy.org/doc/scipy/dev/toolchain.html); [current environment recording](/Users/LOCAL_USER/Documents/src/SwiftSci/Benchmarks/Tools/runner.py:65).

For a paper or shareable result, archive source/input hashes, reference-generation precision, environment lockfiles, seeds and generator state, raw outputs and timings, exclusions, failure records, and the report-generation procedure. A seed alone is insufficient: NumPy's stream guarantee depends on the generator, call sequence, build, machine, and environment, and LAPACK changes can alter multivariate sampling. State separately what can replay bitwise and what should agree statistically. [NumPy compatibility policy](https://numpy.org/doc/stable/reference/random/compatibility.html).
